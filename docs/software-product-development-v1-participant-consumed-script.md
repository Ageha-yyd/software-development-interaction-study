# 软件产品开发实验：参与者可消费的代表性对话稿 v4

这份文件只呈现参与者未来会在 Chat 中真正读到、说出和接续的内容形式。它不是逐字播放脚本，也不是已经发生过的参与者数据：共同前史作为同一项目的既有对话保留在聊天记录里；进入实验后，参与者用自己的话行动，Agent 只能根据当时已经通过发布门的内容自然回应。参与者不会看到 Epoch、节点编号、候选菜单、隐藏评分或其他参与者的路线。

当前状态是 `participant-facing experience witness`：H01–H09 的逐轮来源和新增 Focus/长期观察 packet 仍需完成冻结与 runtime 绑定，因此不能把文中的“结果出来了”当作已经取得的研究证据。下面先给出所有参与者都拥有的同一段项目历史和不计时接管，再给出从同一条最新输出开始形成的三段代表性可能接续。真实参与者只会经历自己实际走出的一段；把它们并排写在这里，是为了审阅“人的注意与动机是否真的改变了项目路径”，不是让一个人从三条路线中选结局。

## 共同前史：这个产品怎样一轮轮成为 R0

**你**

我想做一个很轻的个人阅读清单。场景挺普通的：手机上刷到文章时先留住，回电脑以后再慢慢看。

标签、文件夹还是别的我现在都没想清楚。我最怕的是保存之前还得填一堆东西，最后嫌麻烦干脆不存。先做个足够小、真的能让我用起来的版本吧，别一开始就把它做成知识管理系统。

**Agent**

我先把它压成了一条最短路径：从分享菜单或网页里送进一个 URL，系统补标题和来源，给出明确的保存回执，然后这条内容就能在清单里重新打开。

目前只有 URL 是必需的。Note、Tag 和 Collection 都没有被放进保存门槛里；你可以以后补，也可以一直不补。这个版本已经能完整走通保存和重新打开，但我暂时没有把“保存之后应该停在哪里”当成定论——现在为了方便检查，会进入清单页，这可能和你仍在阅读原文的情境冲突。

所以第一轮真正确定下来的只有一件事：保存首先是捕获，不是整理。之后从哪里接回、未处理内容集中在哪里，还是开放的。

**你**

我刚在手机上连着存了三篇，跳去管理页这一下确实挺打断的。我当时还在看原文，并不想马上处理它。

但也不能存完就消失。我晚上回来的时候，得有个地方能看到今天随手丢进去、还没管过的东西。

**Agent**

我把保存后的行为改了：确认成功后回到原来的阅读任务，不再强制进入管理页；与此同时，新条目会出现在 Inbox，作为“以后还需要处理”的稳定入口。

这里我没有把 Inbox 做成文件夹。它记录的是处理状态：条目仍待处理，或者已经清除。清除 Inbox 不会删除条目。保存时仍然只需要 URL，Note、Tag 和 Collection 继续是可选的。

移动分享和浏览器内保存都重新走过了，回执与返回位置现在是一致的。还有一个语义我先没有替你决定：以后把资料放进某个 Collection，是否就应该自动算作“处理完成”。目前这两件事还没有绑定。

**你**

先别绑。我现在真用起来以后发现，同一篇 **Offline-first sync notes** 既跟 Project Atlas 有关，也跟 Weekend Reading 有关。

我不想为了放进两个地方存两份。那样我以后改 Note，还要猜哪份才是真的。Collection 对我来说更像是不同情境里的归组，不应该拥有一份自己的内容副本。

**Agent**

这里我改的是底层关系，不只是把两张重复卡片视觉上合并。

现在每份内容只有一个稳定的 SavedItem。URL、标题、Note、Tag、来源和修改历史都属于它；Collection 保存的只是这个条目与某个主题之间的 membership。于是同一条资料可以同时属于 Project Atlas 和 Weekend Reading，但从两个地方打开的仍是同一个对象。

我验证了一个关键行为：从一个 Collection 修改 Note，再从另一个 Collection 或 Inbox 打开，看到的是同一次修改，而不是两份逐渐分叉的数据。

这也留下了一个以后需要单独处理的边界：导入旧数据或再次保存相同链接时，什么情况可以安全识别为同一条，什么情况必须让人确认。当前这次修改只确立稳定身份和多重归组，没有静默合并来源不清楚的内容。

**你**

用了几天以后 Inbox 开始变长了。我确实想单独看看哪些东西从来没整理过，但不要把“已经放进 Collection”和“我已经处理完了”混成一件事。

我经常先把资料放进一个项目，周末才认真看；也有些东西我已经看完，不想留在 Inbox，但它根本不值得专门分类。这两种情况都很正常。

**Agent**

你举的两个例子正好说明这里是两个维度，而不是同一条进度。

我增加了 Unsorted：它只表示条目当前没有任何 Collection membership。Inbox 继续只表示条目是否仍待处理。把内容加入 Project Atlas 不会自动清除 Inbox；清除 Inbox 也不会凭空给它创建 Collection。

所以 **Offline-first sync notes** 可以已经属于 Project Atlas、同时仍在 Inbox；另一条临时读完的资料可以已经离开 Inbox、但仍然出现在 Unsorted。四种组合在数据上都合法。

这次形成的是一个受保护的产品语义：以后可以重新设计两个状态怎么呈现，但不能因为界面看起来更简单，就悄悄把处理进度和主题归属合并。

**你**

现在入口开始多了以后，我又不想每次找东西都先回忆“当时到底把它放哪儿了”。

很多时候我只记得标题里有 offline，或者记得自己在 Note 里写过一句话。Search 应该在这些结构之上，而不是某个 Collection 里面的另一个小搜索框。

**Agent**

我把 Search 做成了全局入口，覆盖现存条目的标题、URL、Note 和 Tag，不依赖它是否仍在 Inbox，也不依赖它属于哪个 Collection。

Search 本身不会成为第五份内容仓库。结果仍然指向原来的 SavedItem，所以从 Search、Inbox、Unsorted 或 Collection 打开 **Offline-first sync notes**，对象身份、内容和关系完全一致。

我还分别检查了几种状态：仍待处理但已经归类、已经处理但没有归类、属于多个 Collection，以及只通过 Search 找回。它们都不需要先经过某个“正确页面”。

现在可以确定的是，找回不应要求人先记住产品结构；至于不同入口在真实使用中各自承担什么工作，目前还没有行为证据。

**你**

还有个我不太敢拖到最后的问题：我旧工具里已经有几百条资料，里面有 Tag、来源和一些分组。如果导进来以后只剩一堆平的链接，那这个产品对我其实没有迁移价值。

另外我以前发出去过一些条目的链接。以后就算我们重组页面，也不能让这些链接突然失效；真保不住的话，至少明确告诉我发生了什么，别静默改。

**Agent**

我先用副本做了迁移演练，没有直接写入当前资料。第一次演练确实暴露了两个问题：部分来源信息没有跟着条目进入新结构；一个属于多个分组的条目只恢复了第一条 membership。

这两个问题已经修正。现在导入和再次导出会核对 URL、标题、Note、Tag、来源以及全部 Collection 关系；无法唯一对应的内容会保留为待确认项，不会被猜测性合并。旧深链接则继续解析到原 SavedItem；如果入口结构已经变化，会经过明确的兼容跳转，而不是落到一个看似正常但语义不同的页面。

这轮把数据往返、来源保留和旧链接连续性变成了产品约束。它们不是“迁移工具以后再补”的附属功能，因为一旦失真，前面建立的稳定条目身份也就不可信了。

**你**

我刚又只用键盘走了一遍。鼠标点起来没什么问题，但焦点从编辑框出来以后跳得有点奇怪；手机窄屏上，有些状态也得来回展开才看得明白。

还有，拖放对我可以是快捷方式，但不能是唯一方式。读屏或者键盘用户不能因为我们想让界面更顺手，反而失去整理和撤销的路径。

**Agent**

这次我没有把问题处理成“再加几个提示”。我把关键操作重新走了一遍：保存、清除 Inbox、加入或移出 Collection、全局 Search、查看变更以及撤销。

窄屏下先保留条目身份和主要状态，次要信息按需展开；键盘操作完成后，焦点会回到刚刚发生变化的对象，而不是页面顶部；读屏顺序会先说明对象，再说明当前状态与可执行动作。拖放仍可使用，但所有变化都有菜单或按钮的等价路径，并在提交后给出明确反馈。

我也把这类检查放进了回归门槛：以后任何候选即使改善了主要指标，只要让移动端、键盘或读屏的关键任务出现阻断、不可恢复的语义错误，或者明显增加相同任务的操作与时间成本，就不能被当成可接受版本。

## 共同接管（不计时）：当前参与者用自己的话接回 R0

**你**

我先确认一下我现在对它的理解。

保存只是先把东西留下，不要求我当场整理；Inbox 讲的是还要不要处理，Unsorted 讲的是有没有 Collection；Collection 只是同一条资料和不同主题的关系；Search 可以绕过这些入口直接找原条目。所以归类不等于处理完成，清掉 Inbox 也不等于删除。

如果这层理解没问题，我想先把它当成一个稳定版本，不要因为我们又想到几个功能就继续往上堆。不过你得告诉我：哪些已经证实了，哪些还只是我们觉得合理。

**Agent**

你的理解是准确的。只补一个细节：Unsorted 不是条目上另存的一种状态，而是根据“当前没有任何 Collection membership”得到的视图，所以它不会和真实关系脱节。

已经证实的是当前 R0 的工程行为：URL-only 保存、保存后返回原任务、Inbox 与 Collection 独立、同一 SavedItem 可以有多个 membership、全局 Search 打开原对象、数据往返与旧链接连续，以及移动端、键盘和读屏的关键路径。对应的检查都绑定在这个版本上。

尚未证实的是人们长期使用后究竟在哪里付出最多成本。入口多可能造成上下文重建，也可能是在支持不同任务；较晚整理可能是拖延，也可能正符合“先保存、后理解”；Search、Collections 和状态入口各自承担什么比例，也没有现成答案。

因此我把这个精确状态接受为 R0，但不从它直接推出下一项功能。当前没有正在实施的候选，后续证据需要先说明发生了什么，再由你判断其中哪一部分值得追。

**你**

好，那就冻结 R0。先让一小组按真实方式用几天，不要先塞一个改版给他们。

行为记录和他们自己说的原因分开留着吧。我不想看到一次来回访问，就被系统直接写成“迷路”。

**Agent**

R0 已冻结，后续结果都会绑定到这个版本，不会把未来候选的数据倒回来解释当前产品。

四日材料回来后，表面上没有出现失败：12 位模拟试用者一共保存了 144 个新条目，只填 URL 的路径全部完成；72 次计划内找回也全部成功。但过程没有收敛成同一种用法。48 次延迟找回里有 21 次在打开目标前同时经过 Inbox 和 Unsorted；到第四日，144 个条目中有 57 个已经有 Collection 归属；8 段自愿情境说明则同时出现了“先保存、以后处理”、有意核对两个状态、不确定从哪个入口开始，以及通过 Collection 恢复主题上下文。

行为记录、情境说明、组织时间线、支持与恢复事件，以及工程和可访问性回执都分别保留。成功找回不能证明过程没有恢复成本，经过两个入口也不能直接证明迷路，第四日仍未归类更不能自动算拖延。它们现在构成几个可以继续展开的信息入口，但没有哪一个被预先标成“最值得看”，也没有候选已经进入比较。

## 接续样本 A：参与者注意到状态关系，后来转向长期情境

**你**

找回全成功我先不太在意，21/48 反而有点奇怪。我们之前费劲把 Inbox 和 Unsorted 分开，如果很多人还是两个都开，那我更想先知道他们是在核对，还是根本没理解。这个区别会影响我要不要碰现有语义。

**Agent**

现有八条情境说明只能缩小解释范围，不能给 21 次逐一归因。三条说本来就准备先保存、以后处理；两条明确说是在分别核对“还要不要处理”和“有没有加入主题”；两条说自己当时不确定该从哪里开始；还有一条是通过 Collection 恢复正在做的项目。

所以“有意核对”和“额外恢复”都真实出现了。刚才的 21/48 作为跨入口汇总被这八条说明更新了，但没有被替换成一个单一动机。你过去坚持两个状态独立的决定仍有证据支持，同时“关系是否每次都需要重新想一遍”成为新的未决问题。

如果要继续区分，汇总本身已经不够；现有材料里可以追到某次完整路径、条目当时的两个状态、它此前的组织变化和原始事件。它们回答的是不同层的问题，不会自动合成一个结论。

**你**

给我一条完整的吧，最好是我以前见过的条目。我想先看看一次“两个都开了”实际上长什么样，不要挑最糟的。

**Agent**

有一条是前史里出现过的 **Offline-first sync notes**。它保存当天没有归类，第二天加入了 **Project Atlas**；第四天执行延迟找回时，它仍然在 Inbox。也就是说，它当时同时满足“已经归类”和“仍待处理”，因此不应出现在 Unsorted。

这次实际路径是：打开 Inbox；六秒后打开 Unsorted；十四秒时在 Search 输入 `offline sync`；十八秒时打开正确条目。找回没有失败，也没有生成副本。从 Search 打开的还是原来那条 SavedItem，Project Atlas membership、Note、Tag、URL 和来源都没有被改写。

值得保留的矛盾只在中间：目标实际上不在 Unsorted，但使用者仍去看了一次。日志不能判断这是排除式核对还是入口含义没有恢复起来；十八秒内成功也不能让这次额外访问消失。它是 21 次中的一个实例，不代表其余二十次。

**你**

它都已经进 Project Atlas 了，为什么第四天还留在 Inbox？我知道我们以前说过两个状态独立，但在这个具体例子里还是会下意识把“归类了”理解成“处理过了”。

**Agent**

因为第二天发生的操作只改变了 Collection membership，没有替使用者判断这篇资料是否已经读完、比较完，或者不再需要处理。前史里你给过两个相反情境：先归到项目里、周末再看；以及已经读完但不值得分类。**Offline-first sync notes** 属于前一种，所以“Project Atlas + 仍在 Inbox”是一个正确而非异常的状态组合。

我们当时也考虑过让归类自动清除 Inbox，后来没有采用。那会把主题归组变成处理完成的隐式操作；反过来，让清除 Inbox 自动创建某个 Collection 又会凭空制造组织关系。一个条目还能属于多个 Collection，而处理状态只有一份，强行绑定后既难解释也难撤销。

这次新 trace 没有推翻旧决定，但更新了它的产品代价：语义可以正确，关系仍可能不容易在需要时恢复。它没有回答应该改入口、改说明、加共同视图，还是先保持不动。

**你**

语义别合并。我现在想到的是，能不能偶尔把这两个状态放到同一个地方看，但原来的 Inbox、Unsorted 和 Search 都别拿走。我还会想顺手挑几条稍后归到一个 Collection，不过这不是默认工作流。

**Agent**

我先不直接实现，因为“放到一起看”和“跨两个状态持续保留选择”是两个不同的产品变化。前者只增加一个可选的共同视图；后者会让选择跨页面存活，并把批量操作、范围确认和撤销都带进来。

还有一处会改变验证方式：你说“顺手挑几条”，可以理解为只在当前可见结果里选，也可以理解为切换筛选后继续累积。后一种更灵活，但刚好更容易在离开原上下文后忘记范围。

我目前听到的硬边界是：两个状态不合并；旧入口和 Search 保留；同一 SavedItem 不复制；新区域非默认。你希望第一版只解决共同查看，还是把跨筛选选择和稍后批量整理也一起作为明确的候选能力？

**你**

一起做一版看看吧，不然只看不能整理，我很难知道它是不是真的省事。选择可以跨两个筛选保留，但提交前至少告诉我来自哪里、总共有多少条；做错了必须能整次撤销。

**Agent**

明白。候选的实际范围因此是：一个非默认的联动工作区，同时呈现“仍待处理”和“没有 Collection”两个独立筛选；切换筛选时保留显式选择；可以把所选条目加入一个 Collection。提交前显示操作、条目总数和涉及的筛选，提交后把这次 membership 变化作为一组精确撤销。

我已经在隔离环境完成这一版，并核对了它没有改变 URL-only 保存、保存后返回、条目身份、两个状态的定义、Search、旧链接或导入导出。移动端、键盘和读屏的关键路径也能完成。不过这些只说明候选具备评价资格，不说明联动或批量本身有价值。

R0 仍是当前产品；这个候选没有被接受。接下来的使用结果只属于这份具体实现，包括它的跨筛选选择和只显示数量/来源的提交预览，不能借给以后可能删掉能力的版本。

**你**

范围对。跑它自己的评价。

**Agent**

第一轮没有收敛成“成功”或“失败”。这次输出更新了四块彼此不能互相替代的内容：跨入口重建减少了；窄屏上出现了新的状态误读；批量提交出现了范围撤销；一部分 Search-first 使用者根本没有采用新入口。

具体到顶层结果：同一批任务里，打开目标前再访问另一状态入口从现有版本的 20/48 降到 7/48，活跃步骤中位数从 8 降到 6，回退或请求说明从 9/48 降到 5/48。快速保存 144/144、已知项找回 48/48 仍完成，但它们只是保护项。

新例外包括：12 位试用者中有 2 位在窄屏第一次把两个筛选理解成同一个处理状态；40 次稍后批量整理中有 3 次提交后使用撤销，其中一次是选了 6 条、随后发现多带入 1 条；12 个 Search-first 回访任务中有 9 个继续直接使用 Search。这轮尚未展开那三次撤销的具体范围，也没有长期观察联动区是否会增加维护。

**你**
